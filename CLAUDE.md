# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project
TrialMine: ML-powered clinical trial search engine for oncology.
Patients describe their situation → AI finds relevant trials with explanations.

## Architecture
1. Data: ClinicalTrials.gov API v2 → parse → SQLite + Elasticsearch + FAISS
2. Retrieval: BM25 (Elasticsearch) + Semantic (FAISS with fine-tuned BioLinkBERT)
3. Re-ranking: Cross-encoder (fine-tuned BioLinkBERT) → LightGBM metadata blender
4. Agents: LangGraph — QueryParser → SearchOrchestrator (with tools)
5. Serving: FastAPI backend + Streamlit frontend
6. Monitoring: Prometheus + Grafana
7. Tracking: MLflow experiments

## Tech Stack
Python 3.11+, PyTorch, HuggingFace Transformers, sentence-transformers,
FastAPI, Streamlit, Elasticsearch 8.x, FAISS, LangGraph, langchain-anthropic,
LightGBM, MLflow, Optuna, SciSpacy, Docker, Prometheus + GitHub Actions

## ClinicalTrials.gov API v2
- Base: https://clinicaltrials.gov/api/v2/studies
- Pagination: pageToken (NOT page numbers), pageSize max 1000
- Key paths:
  protocolSection.identificationModule.nctId
  protocolSection.identificationModule.officialTitle
  protocolSection.descriptionModule.briefSummary
  protocolSection.conditionsModule.conditions
  protocolSection.armsInterventionsModule.interventions
  protocolSection.eligibilityModule.eligibilityCriteria
  protocolSection.eligibilityModule.minimumAge / maximumAge / sex
  protocolSection.designModule.phases
  protocolSection.statusModule.overallStatus
  protocolSection.designModule.enrollmentInfo.count
  protocolSection.contactsLocationsModule.locations
  protocolSection.sponsorCollaboratorsModule.leadSponsor.name
- Rate limit: add 0.5s delay between requests

## Coding Standards — IMPORTANT
- Type hints on ALL public functions
- Pydantic models for ALL data structures
- YAML configs for hyperparameters — NEVER hardcode magic numbers
- Structured JSON logging via Python logging module — NEVER use print()
- Error handling: NEVER let the API return 500. Always return structured error responses.
- Every function that calls an external service (API, DB, file) MUST have try/except
- Tests for all data parsing and feature engineering functions
- Docstrings on all public classes and functions

### What's working
- **Data pipeline**: downloads oncology trials from ClinicalTrials.gov API v2, parses, stores in SQLite
  - `scripts/download_data.py` → `data/trials.db` (140,723 trials)
- **BM25 search**: Elasticsearch index with 140,723 trials (596 MB), searchable via API
  - `scripts/build_index.py` → Elasticsearch `trials` index (requires Docker)
  - `src/TrialMine/retrieval/bm25.py` (ElasticsearchIndex — create, bulk index, search with field boosting, get_trial)
- **Semantic search**: Fine-tuned BioLinkBERT embeddings + FAISS index
  - `scripts/build_index.py --skip-bm25 --model fine-tuned` → `data/faiss_finetuned.index` (412 MB) + `data/faiss_finetuned.json`
  - `scripts/build_index.py --skip-bm25 --model off-the-shelf` → `data/faiss_offshelf.index` (412 MB) + `data/faiss_offshelf.json`
  - Model aliases: `--model off-the-shelf` → `michiyasunaga/BioLinkBERT-base`, `--model fine-tuned` → `models/embeddings/fine-tuned`
  - `src/TrialMine/models/embeddings.py` (TrialEmbedder — mean-pooled BioLinkBERT, explicit Transformer+Pooling for non-ST models to avoid SIGSEGV)
  - `src/TrialMine/retrieval/semantic.py` (FAISSIndex — cosine similarity via IndexFlatIP)
  - Fine-tuned: cosine spread 0.51–0.61 in top 5 (was 0.047 range pre-tuning), hub trial problem eliminated
- **Hybrid search**: Reciprocal Rank Fusion (RRF, k=60) combining BM25 + semantic
  - `src/TrialMine/retrieval/hybrid.py` (HybridRetriever — 200 candidates per method, RRF fusion, metadata enrichment)
  - Each result tagged with source: "bm25_only", "semantic_only", or "both"
- **FastAPI backend** (port 8000): POST /api/v1/search (method: bm25|semantic|hybrid), GET /api/v1/trial/{nct_id}, GET /health

### Design decisions (Week 11+ — Phase 13A UMLS HOLD)
- **Decision 41** — Revert (hold at default-OFF) on the UMLS drug-class matcher despite shipping Phase A clean. **Why:** Phase B re-eval on 30 complex+vague held-out queries returned aggregate-tied (complex NDCG@5 Δ=−0.012 within CI half-width ~0.09; vague Δ=0.000) AND surfaced a **structural false positive** on the Q413 spot-check. Trial `NCT03755102` excludes prior `dacomitinib therapy` but the UMLS class bridge linked dacomitinib + osimertinib via the shared EGFR-TKI class CUI (C5574906 / C1268567), causing the trial — *actually* a study of dacomitinib+osimertinib FOR osimertinib-failure patients — to be wrongly dropped under UMLS-on. The bridge is "right" for class-level exclusions ("no prior EGFR TKI" — patient's osimertinib correctly resolves to the class) and "wrong" for drug-specific exclusions ("no prior dacomitinib" — trial author meant a specific drug, not the family). Parsed-eligibility text can't disambiguate — both look like a string in `excluded_prior_treatments`. Q417 (pembrolizumab ↔ ICI exclusion) worked correctly as the canonical case, but 1-of-2 spot-checked drops being a clinical false positive is a structural red flag, not a coverage gap. **How to apply:** future class-bridge work needs **per-criterion specificity** — knowing whether a trial author meant a specific drug or the class. Three paths, all deferred: (a) UMLS REST API with hierarchy walks (`umls_api_key` field already on `Settings`, currently empty); (b) RxClass / NCIt fallback via `scispacy_linker.linker_name="rxnorm"`; (c) per-trial LLM call at matching time. Until one of those lands, drug-class matching at the eligibility-filter level is too imprecise to ship. **Trade-offs:** zero revert cost — `umls_drug_class_matching_enabled` defaults to False, production was never affected. All Phase A code (linker singleton, `link_to_cuis` / `match_via_cui`, `DRUG_TO_CLASS_CUIS` table, abbreviation handler, toggle, tests, runbook) stays installed. Re-enabling is one flag flip; re-eval is ~$0.30 Haiku. **What this does NOT solve:** the persistent `complex` weakness — 5/15 complex queries don't mention a specific drug at all (Q601/Q606/Q607/Q608/Q609), so UMLS would never have helped them regardless; for the remaining 10, the bottleneck is now diagnosed as structural rather than coverage. Next intervention candidates documented in `docs/things_can_be_fixed.md` §7. **Process lesson worth keeping:** the runbook's Phase C decision gate (holistic review of 6 signals + spot-check) caught a failure that the aggregate metric alone wouldn't have — Δ=−0.012 is "tied" in any reasonable read of the bootstrap CIs, but Q413's spot-check found the clinical false positive that justifies HOLD over SHIP-anyway-with-writeup. Always spot-check the canonical cases before deciding on holistic gates.

### Design decisions (Week 11 — Phase 12 LightGBM ranker v3-regularized)
- **Decision 40** — LightGBM ranker retrained on the v2 stack's features (v2 bi-encoder + v2 FAISS + v2 CE), with **anti-concentration regularization** to prevent the LGB from collapsing onto the dominant `cross_encoder_score` feature. **Why:** Phase 11 shipped v2 CE today; the prior v2 LGB was trained on v1-era features, so its learned blend weights no longer matched the production feature distribution. The 3-way ablation made the cost explicit: 65q `+LGB` regressed from **0.783 (pre-Phase-11, v1 stack + v2 LGB) → 0.761 (current prod, v2 stack + stale v2 LGB)** — a silent −0.022 NDCG@5 regression introduced by the Phase 11 ship itself. Vanilla retraining (v3) over-fit catastrophically: LOOCV NDCG@5 jumped to 0.989 but held-out 65q NDCG@5 dropped to **0.697** (worse than v2 LGB). Diagnosis: the labeled-pool training distribution is too kind to a strong CE — when v2 CE arrives, LightGBM correctly learns "trust CE almost exclusively" and the feature-importance ratio shoots to 7.2× (CE 4810 vs next-highest rrf_score 666). At held-out time on hybrid top-50, the LGB needs metadata signals for tiebreaking that it stopped learning. **Path-1 fix:** `feature_fraction=0.5` (was 0.8) + `feature_fraction_bynode=0.5` (was 1.0) + `lambda_l2=1.0` (was 0) + `min_data_in_leaf=50` (was 5) + `num_boost_round=100` (was 200). The single most effective lever is column subsampling — at 0.5 each tree only sees half the features, so half the trees can't even use CE and must learn metadata patterns. The ensemble averaging recovers a balanced ranker. **Held-out result:** 65q `+LGB` NDCG@5 = **0.794** (restores monotonic +LGB improvement, exceeds pre-Phase-11 by +0.011), 20q expansion `+LGB` = **0.526** (+0.076 above pre-Phase-11; LGB layer adds +0.113 over +CE — single biggest marginal lift in the entire pipeline ablation on the hard slice). **How to apply:** when any upstream feature-source ships (bi-encoder, FAISS, CE), schedule an LGB re-fit BEFORE closing the cycle — features go stale silently. Add `--regularize` to `scripts/train_ranker.py` and produce a 3-way ablation (pre-stack + LGB / new-stack + stale LGB / new-stack + new LGB) on the held-out before deciding to ship. Vanilla retrain is NOT enough; need column subsampling + L2 to prevent feature collapse. **What this does NOT solve:** the "is the LGB blender architecturally necessary?" question remains open — pure v2 CE on hybrid top-50 scored 0.553 (lost by −0.21 to LGB), but that gap is heavily confounded by label coverage (LGB learned to surface labeled-pool candidates). Resolving it cleanly needs a pooled TREC-style labeling at ~$115; deferred. Per-category regression flagged honestly: treatment −0.117 on n=4 (wide CI; below the "ship" threshold but holistic decision-36-framing wins).

### Design decisions (Week 11 — Phase 11 cross-encoder v2)
- **Decision 39** — Cross-encoder trained on graded `(query, pos, neg, margin)` triplets with `MarginMSELoss`, replacing v1's binary `BinaryCrossEntropyLoss`. **Why:** v1 converged to a disease/intervention matcher whose val metric (`CERerankingEvaluator_ndcg@10`) saturated at 0.993 on 1-pos/1-neg sub-tasks — completely non-predictive of production ranking quality (v1 pure CE NDCG@5 = 0.789 on the held-out 65-query benchmark, *worse than the hybrid RRF baseline of 0.837*). The 16-pt val/prod gap meant we couldn't iterate on CE quality with the existing val signal; the binary objective also meant CE couldn't distinguish "fairly relevant" from "very relevant" (it could only say "relevant or not"). Switching to graded labels + MarginMSE collapsed the val/prod gap to 3–8 pt (val 0.943 → prod 0.86–0.91), and v2 pure CE jumped to **NDCG@5 = 0.898** on the same held-out benchmark — Δ = +0.109 with non-overlapping CIs. **How to apply:** graded labels exist scattered across 4 source JSONL files; see `scripts/build_ce_graded_training.py` for the build recipe (margin = grade(pos) − grade(neg) ∈ {1, 2, 3}; query-level 80/20 split with seed=42 holding out the 85 qids in `full_labeled_dataset.jsonl` + `full_labeled_dataset_expansion_v2.jsonl`). Init choice (warm-start from v1 binary CE vs cold-start from base BioLinkBERT) was settled empirically by the Phase B sweep — cold won by 0.0003 NDCG@10 (effectively tied), and cold is the methodologically cleaner pick since the experiment exists to fix v1's binary-CE noise. **Blender ceiling lifted as a corollary:** the C3 α sweep with v2 CE wired in showed lower α (more CE weight) monotonically improves NDCG, so the production default flipped from 0.7 (RRF-dominant, the v1-era safety cap) to 0.3 (CE-dominant) — `rerank()` now takes an `rrf_weight` parameter so future tuning is a single override. **Decision-gate framework**: holistic review across 7 signals (blended NDCG, pure CE NDCG, val/prod gap, per-category drift, blender α winner, init winner, cost-of-revert), no rigid pre-registered thresholds — same Decision-36 framing the bi-encoder v2 ship used. **What this does NOT fix** (per Issue #5's own honest prediction): queries whose intent lives in eligibility text (Q413 / Q416 — `failed osimertinib`, `post-trastuzumab progression`) need parser-quality work (UMLS via SciSpacy `EntityLinker`, Decision 18 upgrade path), not better CE. CE on full-trial text can't see fields the bi-encoder + parser didn't surface. v2's complex slice lifted 0.420 → 0.684 (+0.264) — real improvement, still well below the common/treatment ceiling.

### Design decisions (Week 10 — Phase C5 eligibility hard-filter)
- **Decision 38** — Eligibility hard-filter only on closed-vocab criteria (`age`, `sex`, `excluded_prior_treatments`). The full Met/Unmet/Unknown verdict from `check_trial_eligibility` is a roll-up over 5+ criteria with wildly different precision: `age` (numeric) and `sex` (enum) have >95 % precision, but `required_conditions` (SciSpacy NER) is ~70 % (false-matches "Histologically", "signed", "ICF") and `required_prior_treatments` (literal string match) misses drug-class equivalences ("osimertinib" ≠ "systemic therapy"). The first filter implementation used the overall verdict — Q413 smoke test dropped 10 of 10 trials because the noisy criteria triggered everywhere. **Why this matters:** filtering on the overall verdict optimizes for precision at zero recall (everything looks Unmet); filtering on closed-vocab criteria only optimizes for precision at modest recall (4 of 30 queries trigger, lifting 2-3 of them by +0.075 to +0.10 NDCG@5). Soft criteria are still surfaced in the response annotation so users see the full Met/Unmet/Unknown explanation — they just don't trigger drops. **How to apply:** when adding a new criterion to the verdict logic, run a smoke test on Q413 + Q416 (the canonical complex failures) and check that the false-positive rate doesn't blow up before adding it to `HARD_FILTER_CRITERIA` in `src/TrialMine/features/eligibility_filter.py`. The same module is imported by both the live orchestrator (Step 5b) and the eval script (`build_full_eval_dataset.py --apply-eligibility-filter`) so the production rule and the offline measurement agree.

### Design decisions (Week 10 — Phase A/B/C bi-encoder retrain + ship)
- **Decision 33** — Synthetic queries are generated via 6 SHAPE_PROMPTS rotated round-robin (failed_treatment, post_progression, biomarker, multi_constraint, vague, caregiver) instead of one generic prompt. **Why:** v1's eval revealed that complex and vague were the two weakest slices, and the 1.5K synthetic queries v1 trained on were essentially all the same shape ("query about cancer type X"). Hypothesis was that more shape diversity in training would help the model handle shape diversity at inference. **How to apply:** when expanding the eval set, mirror the shape proportions used at training time — the eval table in `docs/evaluation-report.md §8` shows that this hypothesis was right for `vague` (+0.048 NDCG@5) and wrong for `complex` (-0.014), so the training-mix design should be evaluated PER SHAPE not just in aggregate. The retrospective lesson is that complex failures are pipeline-level not representation-level — more diverse training data cannot fix them.
- **Decision 34** — Per-group floor of 300 trials for rare-cancer categories, implemented with **with-replacement sampling** when the corpus per group is below the floor. **Why:** v1's 22-key cancer taxonomy treated medulloblastoma, Wilms, GIST, and neuroendocrine as fold-ins under generic buckets, which meant the bi-encoder never saw enough rare-class contrast pairs to learn fine-grained distinctions; v1's `rare_explicit` queries were essentially OOD. With-replacement sampling is needed because some buckets have < 300 trials in the corpus. **Mitigation of with-replacement risk** is the 6-shape rotation from Decision 33: the same trial gets paired with 6 different query shapes, so we don't memorize a specific (query, trial) pair. **How to apply:** before adding a new rare-class bucket, check `data/trials.db` for corpus size with `SELECT COUNT(*) FROM trials WHERE condition LIKE '%X%'`; if < 300, expect with-replacement and ensure the synth-shape diversity is in place to dilute the duplication.
- **Decision 35** — Taxonomy expansion from 22 → 31 keys with **sarcoma split into 4 sub-buckets** (bone, pediatric, soft_tissue, other) and 6 new first-class types (medulloblastoma, Wilms, GIST, neuroendocrine, biliary, MDS). **Why:** v1's "sarcoma" bucket was a 1,800-trial fold-in mixing osteosarcoma, leiomyosarcoma, rhabdomyosarcoma, and others — pairs within the bucket had ambiguous semantics, hurting the contrast signal. Same for the implicit fold-ins of medulloblastoma → "brain", GIST → "GI", etc. Finer taxonomy means cleaner negatives. **Trade-off:** finer taxonomy also means the bi-encoder must distinguish more fine-grained categories, which makes evaluation harder (this is consistent with v2's val set being modestly harder than v1's — see `docs/evaluation-report.md §8` discussion). **How to apply:** taxonomy fixes are zero-cost to revisit between training runs; revisit when a new evaluation slice (e.g., a category from the labeled set) shows persistent confusion that maps to taxonomy ambiguity.
- **Decision 36** — Ship v2 despite missing the pre-registered complex and vague gates. **Why:** Overall NDCG@5 / NDCG@10 are tied with v1 within bootstrap noise (Δ ≈ 0 on both), v2 has real per-category wins on `vague` (+0.048) and `geographic` (+0.063), no-regression floors on common/rare/treatment are all comfortably cleared, and the new `rare_explicit` slice lands at 0.747 vs ≥0.55 floor. The strict letter of the runbook's REVERT decision matrix was honored as the methodologically clean path, but the override is documented in `docs/evaluation-report.md §8` because (a) reverting trades a tied headline for the same tied headline (no measured cost), (b) the complex failure is diagnosed as a pipeline-logic gap (eligibility-filter not used as hard retrieval filter), not an embedding gap — so v1 has the same problem, and (c) discarding the cleaner training data + the partial success on vague is a sunk-cost loss the project doesn't recover from. **How to apply:** future ship/revert calls follow the same template — if the pre-registered gate fails BUT overall is tied AND there's a real per-category win AND the failure mode is diagnosed as out-of-scope for the experiment's lever (i.e., the right fix is in a different layer), ship and document. Don't move the goalposts; do override transparently.
- **Decision 37** — Phase C4 expanded the eval to n=15 per category for complex+vague (added 10 queries each, IDs 600-619) instead of accepting the n=5 statistically-undecidable result. **Why:** at n=5 the bootstrap CI half-widths were ±0.13–0.15, wider than the gap from gate threshold. Both v1 baseline (0.626) and v2 (0.609) sat INSIDE the 95% CI of "passes 0.68" — undecidable. Adding 10 more queries each pushed CIs to ±0.10–0.13 and revealed that BOTH v1 and v2 were significantly below 0.68 on the expanded set (v1 0.540, v2 0.526). The original n=5 numbers were overestimating absolute capability by 8-10 points on complex. **Why we labeled BOTH pipelines on the new queries:** apples-to-apples comparison requires the same query set for both; labeling only v2 on the expansion would have biased toward v2 by comparing against a noisier v1 baseline. **How to apply:** if a per-category threshold falls inside the bootstrap CI of the point estimate, the decision is undecidable at that sample size — expand the eval before deciding (cost: ~$0.04 per added query pair × top-K × 2 pipelines). This is NOT moving the goalpost — it's tightening the measurement before reading it.

### Design decisions (Week 9)
- **Decision 31** — 60 queries × top-20 = 1200 labeled pairs is the *minimum* sample size that gives us interview-defensible bootstrap CIs at the per-category level. The overall NDCG@5 CI on n=60 is ±0.04; per-category CIs land at ±0.03 to ±0.32 depending on the category sample (n=3 to n=30). Anything smaller (e.g., the original 20-query set with ±0.10 CIs) lets a single query swing the headline by 5 pts and gets pushed back on by anyone who's ever stared at a noisy AB test. Anything larger (e.g., 200 queries) costs ~3× the API spend for ~30 % tighter CIs — diminishing returns once the headline is already statistically loaded. **Why:** in interviews and design-review, "is your evaluation noisy?" is the second question after "what did you measure?" Bootstrap CIs reported in the headline table close that loop preemptively. **How to apply:** when adding new evaluation slices (fairness, location, language), aim for ≥ 5 queries per slice so the per-slice CI half-width stays under ±0.20; budget ~$0.02/labeled pair × top-K when projecting cost.
- **Decision 32** — LLM-as-judge limitations are documented *honestly and in the headline*, not hidden in a methodology footnote. Three explicit caveats in `docs/evaluation-report.md`: (a) both judges are LLMs (no human gold standard), (b) labels were drawn from the pipeline's own output so §3 NDCG measures *list ordering*, not *recall*, (c) `complex` shows 0 theirs-only against CT.gov because CT.gov's top-20 left our 140 K oncology-only index — that is a coverage gap on our side, not a CT.gov failure. The headline kappa (κ = 0.72) and the precision delta (+9.8 pts) are reported alongside the caveats, not after them. **Why:** interviewers immediately distrust evaluation reports that sound too clean — a well-calibrated "here's what this number doesn't tell you" paragraph builds more trust than a clean number alone. The Haiku-systematically-over-rates-top-tier finding from the Sonnet kappa is the kind of thing an honest reviewer wants surfaced; hiding it would invite the question and lose the interaction. **How to apply:** every new evaluation report ships with §Limitations as a first-class section listing (i) sample size + CI width, (ii) label provenance + judge identity, (iii) anything the metric cannot measure. Refuse to publish a metric without the matching caveat.

### Design decisions (Week 8)
- **Decision 29** — Test our code, not third-party internals. Unit tests assert behaviour we own (parsing rules, RRF math, filter logic, route shapes); the LLM call inside `QueryParserAgent.parse` is mocked at the SDK boundary in `tests/unit/test_parse.py`. Two reasons: (a) re-running Haiku for every CI build is slow + costly + flaky, and (b) the LLM's output is non-deterministic — `assert profile.condition == "X"` would fail randomly even when nothing in our code changed. Quality of LLM extraction is held to account by the labeled-eval pipeline (`data/evaluation/labeled_queries.jsonl` + `scripts/evaluate.py`), where graded relevance + bootstrap CIs handle non-determinism correctly. **How to apply:** if a test would have to mock more than three layers of a third-party library (network → SDK transport → response parsing → schema), that test is in the wrong place — move the assertion into an offline eval over labeled examples.
- **Decision 30** — A/B test router (`src/TrialMine/experiments/ab_test.py`) shipped as an interface stub, not a working experimentation backend. The interface is the load-bearing piece: deterministic SHA-256 bucketing on `f"{experiment}:{subject_id}"` so traffic is independent across experiments, Pydantic-typed Experiment / ExperimentVariant for compile-time validation, and `log_exposure()` as a single seam where future telemetry (BigQuery / Kafka / Datadog) plugs in without touching call sites. Today exposures land in an in-memory list; one swap turns this into a real backend. Trade-off: this is *production-thinking signal*, not production code — there's no bandit allocation, no traffic-quota tracking, no analysis pipeline yet. Doing those right needs real outcome data, which comes after the first real users. **How to apply:** when wiring an experiment into the ranker / agent, route via `ABTestRouter.route(...)` and call `log_exposure(...)` at the same site so the exposure→outcome join is unambiguous.

### Design decisions (Week 7)
- **Decision 24** — Streamlit over React for the patient-facing UI. Single Python file collapses no-JS-toolchain + no-API-client + no-state-management. The agent_trace expander, conditional sidebar (filters hide when AI agent toggle is on), session-state-driven examples, and rank-based match% progress bars all shipped in one pass. Trade-offs: `st.columns(5)` doesn't reflow on narrow viewports (mobile is cramped), no granular component control, and Streamlit-specific patterns (form `on_click` handlers, reruns, `cache_resource`) can be inscrutable to non-Streamlit reviewers. Trigger to migrate to React / Next.js: real concurrent users, mobile-first requirement, or token-by-token streaming surface (Streamlit's rerun model fights live-stream UIs).
- **Decision 25** — Docker Compose, not Kubernetes. Single host, one `up --build` command, no operator burden. Six services with healthcheck-driven `depends_on` (api waits on ES + redis healthy; ui waits on api started; grafana waits on prometheus). Compose YAML does NOT translate to K8s manifests — migration path is Helm or Kustomize, not copy-paste. Trigger to migrate: >1 host, autoscaling, rolling deploys, multi-tenant. **Caveat (TODO):** no `restart:` policy declared on any service yet — add `restart: unless-stopped` if the stack is meant to live longer than a few hours unattended.
- **Decision 26** — ES heap = 1 GB (`ES_JAVA_OPTS=-Xms1g -Xmx1g`). 140,723 docs indexed, ~596 MB on disk. 1 GB heap gives comfortable headroom for query cache + filter cache + segment metadata. 512 MB sits below ES 8.x's recommended floor for non-trivial datasets and risks OOM under bulk-index or aggregation load — the choice is precaution, NOT measurement (did not benchmark 512 MB OOM directly). If host RAM becomes constraint-bound, the measurable next step is 768 MB.
- **Decision 27** — `OMP_NUM_THREADS=8` in the Linux container, overriding the project's macOS-host default of `=1`. The original `=1` was set to avoid the macOS FAISS + LightGBM OpenMP runtime collision (Apple Accelerate's libomp + faiss-cpu's libomp double-loading → SIGSEGV). Inside the Linux container both libraries link against glibc's libgomp1 and coexist without crash. Empirical impact: with `=1`, the BioLinkBERT cross-encoder was single-threaded and took ~30 s/call for 50 candidates; with `=8`, ~4–8 s, fitting the 15 s agent budget. **Note for host-Python runs**: keep `OMP_NUM_THREADS=1` for `python scripts/...` invocations on macOS — the container value doesn't help, and the host conflict still applies.
- **Decision 28** — Filter at the post-RRF candidate level, NOT at the semantic-search call. FAISS has no native filter primitive; semantic returns top-K by cosine regardless of status. The original `HybridRetriever.full_pipeline` only passed `filters=` to BM25, and well-described COMPLETED trials leaked in via the semantic side — dominating top-10 even when `filters={"status": "RECRUITING"}` (8/10 COMPLETED in the lung-cancer demo run on 2026-05-07). Fix: after RRF merge, drop semantic-only candidates whose ES metadata doesn't match the filter; BM25 hits fast-path through (already filtered). Cost: 1 extra `get_trial` ES call per semantic-only candidate that survived RRF — typically 50–100 calls × ~5 ms ≈ 250–500 ms added latency. Alternative considered: pre-filter semantic side with one ES mget — faster but couples the retriever to ES's mget API; rejected as premature optimisation. After the patch: 10/10 RECRUITING for the same query, "completed melanoma trials phase 3" still correctly returns COMPLETED via the existing keyword-override path.

### Design decisions (Week 6)
- **Decision 20** — LangGraph `StateGraph` over CrewAI / raw function calling. The flow is *deterministic* (parse → search → explain → fallback), not open-ended reasoning. State machine gives explicit conditional routing (`execute_search → fallback_search` on error), structured agent_trace via the `operator.add` reducer, and per-node testability. CrewAI's role-based abstraction is overhead for a fixed flow; raw function calling lacks the conditional-routing primitive and would re-implement what `StateGraph` provides.
- **Decision 21** — Claude Haiku 4.5 for slot extraction. Extraction task, not complex reasoning — Sonnet/Opus are overkill. Measured ~1.3–1.5 s warm latency and ~$0.0017/query (slightly above the original aspirational <1 s / $0.001; baseline Haiku 4.5 runs hotter than the napkin claim, but quality is 10/10 on test queries so the budget is fine). Cost dominated by ~1370-token input prompt; trimming the prompt would risk extraction quality regressions. Prompt is below Haiku 4.5's 4096-token cache threshold so prompt caching is a no-op for now.
- **Decision 22** — Two LLM-using components, not three (template explanations). LLM-per-result would add 10–20 s and ~$0.05 per query for marginal quality gain on this surface. Templates render in microseconds and surface the eligibility verdict counts directly (`Eligibility: likely a Match (5 met, 0 unmet, 1 unknown)`). Future option: one batched summarization pass over the top 3 explanations if user feedback shows the templates are too terse.
- **Decision 23** — 15 s wall-clock budget + fallback path. The pipeline always returns a structured `SearchResponse` — never a 500, never an unhandled exception. Quality degrades gracefully: agent path → `fallback_search` (plain hybrid, no eligibility) → empty results with `error` reason set. *The contract guarantees response shape, not non-empty results*: empty `results: []` is a valid outcome when ES is fully down or the input matches nothing. Conditional fallback fires only on system errors (`execute_search` exception), not on empty primary results — empty is treated as a legitimate answer, not a failure to mask.

### Design decisions (Week 5)
- **Decision 17** — SciSpacy + regex hybrid for eligibility parsing, NOT custom NER. Custom NER ≈ 80–120 hr; hybrid ≈ days at ~70% precision. Best accuracy/effort.
- **Decision 18** — Hand-built ~45-entry synonym dict, NOT UMLS yet. Covers 23-cancer taxonomy. UMLS via SciSpacy `EntityLinker` is target after dict outgrows ~50 entries. Each entry must be lay→broader medical (never narrower); no chained mappings; no replacements that collide with verbatim trial vocabulary.
- **Decision 19** — Eligibility checker (future, not yet built) will emit Met / Unmet / **Unknown** verdicts, not binary. Binary on partial info produces confidently-wrong outputs. Trial-level rollup rule: any hard Unmet → trial Unmet; all Met → Met; else Unknown. Distinguish parser-unknown (low parse_confidence) from patient-unknown (missing patient field) — same label, different UX.
